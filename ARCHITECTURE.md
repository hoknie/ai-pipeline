# Архитектура ai-pipeline — регламент

Этот документ — **правила раскладки кода**: где что лежит, кто от кого зависит, как добавлять
новое. Поведение программы он не описывает; причины правил названы здесь коротко, рядом с самими
правилами.

Документ задаёт **целевую** раскладку. Код переходит к ней по шагам, и пока переход не закончен,
часть правил держится на списке исключений: что уже сделано, а что ещё нет — в §13. Новый код
пишется сразу по этим правилам, даже если сосед по папке им ещё не следует.

Образец — регламент сервиса `svc-registry`: фичи, платформа, представление, единая сборка. Правила
перенесены на TypeScript и на устройство `aip`; отступления перечислены в §11.

---

## 0. Как читать этот документ

| Термин                | Простыми словами                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Пакет**             | Один npm-пакет на весь репозиторий (ESM). Бэкенд — `src/`, панель — `web/`.                                                                       |
| **Точка входа**       | `src/cli/main.ts`: читает `process`, передаёт управление в `presentation/cli`. Других файлов в `src/cli/` нет.                                    |
| **Фича**              | Каталог `src/feature/<фича>` со всем, что нужно одной области: виды папками (`types/`, `ports/`, `services/` и другие, §5).                        |
| **Вид**               | Папка внутри фичи с одним назначением. Вид определяет, что можно импортировать.                                                                   |
| **Сервис области**    | Класс в `<фича>/services` на одну область со своими зависимостями. Набор областей фичи — единственный вход в неё для представления и других фич.   |
| **Машина состояний**  | `feature/runs/machine`: чистая функция `transition(state, event)`, которая возвращает новое состояние и эффекты. Единственный способ изменить запуск. |
| **Эффект**            | Описание действия, которое вернула машина: запустить или остановить специалиста, сделать коммит, слить группу. Исполняет его сервис, а не машина.  |
| **Репозиторий**       | Тип в `<фича>/repositories`: только доступ к данным (SQL или файлы) и отображение строк, без решений. Не путать с git-репозиторием пользователя.     |
| **Порт / адаптер**    | Интерфейс, который фича ждёт (объявлен у потребителя), и его реализация (в `clients/` или сервис другой фичи).                                    |
| **Платформа**         | `src/platform`: git, SQLite, процессы, пути, ошибки. Инфраструктура без правил `aip`.                                                             |
| **Представление**     | `src/presentation`: IPC, MCP, CLI, веб-сервер. Принимает вход, отдаёт ответ, ничего «умного» не решает.                                           |
| **Сборка**            | `src/app` — единственное место, где всё соединяется в работающее приложение. Отсюда начинают чтение.                                              |

Главная мысль: **граница — это граница импорта**. Фича не импортирует представление и чужие
репозитории, платформа — фичи. Правила держат проверки в `test/`, а не договорённость.

## 1. Принципы

1. **Демон владеет состоянием.** CLI, MCP и панель — клиенты демона через Unix-сокет.
2. **Состояние запуска меняется только через `transition`.** Машина чистая: она не читает часы и
   файлы, а получает всё на вход и возвращает эффекты. Поэтому её можно проверять без git и агентов.
3. **Фичи, платформа, представление; зависимости в одну сторону:** представление → фичи (по
   ацикличному графу) → платформа.
4. **Сборка одна** — `src/app`. Ни один класс не создаёт свои зависимости сам: фича собирает свои
   сервисы и репозитории в `services/create.ts`, а вызывает эту функцию только `app`.
5. **Чистота проверяется по всей цепочке импортов.** Файл чистого вида не должен тянуть `node:*`
   даже косвенно, через чужой реэкспорт.
6. **Границы процессов проверяются схемами zod:** IPC, MCP, вывод CLI агентов. `swarm.yaml`
   проверяется с путями полей.
7. **Сначала стандартная библиотека.** Каждая новая зависимость взвешена, версии точные.
8. **Окружение читают только точка входа, сборка и платформа.** Остальные получают значения
   параметрами, поэтому тесты не трогают окружение процесса.
9. **Качество — гейт:** `npm run check` проходит перед завершением любой работы.
10. **Правило о размещении кода держит проверка.** Импорты, чистота, пакеты, создание сервисов, виды
    папок, пределы и окружение проверяет `test/layout`, и новое такое правило приходит вместе с
    тестом. Правила о смысле (что считать решением, как делить область) проверить нельзя: их держит
    ревью, и в тексте они записаны как рекомендация с причиной.

## 2. Топология репозитория

```
ai-pipeline/

├── justfile, env/justice/   # рецепты
├── scripts/                 # установка, выпуск, фоновая панель
├── templates/, examples/    # шаблоны init, пример swarm.yaml (его проверяет тест)
├── integrations/            # плагин Claude Code
├── docs/                    # документация пользователя
├── src/
│   ├── cli/main.ts          # точка входа; путь не меняется, на него указывают установленные команды
│   ├── app/                 # сборка (§4)
│   ├── feature/             # вся логика: §5 и граф ниже
│   ├── platform/            # инфраструктура без правил aip (§4)
│   └── presentation/        # ipc, mcp, cli, web (§4)
├── test/                    # vitest; повторяет раскладку src/; сквозные — test/daemon, test/cli
│   ├── fakes/               # поддельные claude и opencode
```

### Направление зависимостей

```
        node:*, пакеты по таблице §8
                   ▲
   src/platform/*                         не импортирует фичи, представление, app
                   ▲
   src/feature/<фича>                     граф фич ниже
     ├─ types/                            чистый; свои types, types фич по графу, platform/errors
     ├─ machine/                          чистый; только runs: свои types, types фич по графу, platform/errors
     ├─ ports/                            интерфейсы; импортирует types
     ├─ repositories/                     доступ к данным; platform; его импортирует только своя фича
     ├─ usecases/                         крупные сценарии; их вызывает только services своей фичи
     ├─ services/                         platform, свои виды, types и services фич по графу
     └─ clients/<адаптер>/                реализует свой порт; platform; его импортирует только app
                   ▲
   src/presentation/ipc/contract          platform, types фич; ipc/client и ipc/views запрещены
   src/presentation/ipc/client            platform, ipc/contract, types фич
   src/presentation/ipc (остальное)       platform, ipc/contract, types, ports и services фич
   src/presentation/format                ipc/contract, types фич
   src/presentation/web                   platform, ipc/contract, ipc/client, types фич
   src/presentation/mcp                   то же и format
   src/presentation/cli                   то же, что mcp, и app; services только у swarm-config;
                                          presentation/mcp и presentation/web — только их index.ts
                   ▲
   src/app                                собирает всё
                   ▲
   src/cli/main.ts → presentation/cli
```

Граф фич (импорт разрешён только по стрелкам, ацикличен):

```
swarm-config
repos
agents      → swarm-config
tags        → repos
runs        → agents, repos, swarm-config
swarm-edit  → agents, repos, runs, swarm-config
artifacts   → runs
delivery    → runs, swarm-config
processes   → runs
queue       → runs, tags, repos, swarm-config
observers   → queue, runs, repos, swarm-config
stats       → runs, repos, swarm-config
integrations → repos
identity    → swarm-config
compose     → observers, queue, runs, tags, repos, integrations
```

| Фича           | Область                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| `swarm-config` | модель специалистов и конвейеров, поиск настроек, слияние уровней, проверка, чтение `swarm.yaml`        |
| `swarm-edit`   | правка конфигурации из панели, общие специалисты и конвейеры, теги специалистов                        |
| `agents`       | порт агента, адаптеры `claude` и `opencode`, права, расшифровка вывода, каталог навыков                |
| `tags`         | каталог тегов задач; связку тегов с запусками и очередью держит `queue`                                |
| `repos`        | реестр git-репозиториев пользователя и приведение пути к корню; счётчики запусков считает представление |
| `runs`         | запуск, группы, шаги, стадии; машина состояний, диспетчеризация, исполнение эффектов                   |
| `artifacts`    | артефакты шагов                                                                                        |
| `delivery`     | доставка результата в рабочее дерево, патчи и диффы групп                                              |
| `processes`    | фоновые процессы агентов                                                                               |
| `queue`        | очередь задач, зависимости, места, пауза, теги запусков и элементов очереди                            |
| `observers`    | наблюдатели и группы ремонта                                                                           |
| `stats`        | журнал использования агентов (токены, время) и отчёт по нему                                           |
| `integrations` | подключения к внешним системам: реестр, секреты через порт хранилища, вход событий с проверкой и дедупликацией |
| `identity`     | пользователи режима сервера, сессии панели, личные токены, ссылки входа и вход из CLI                  |
| `compose`      | сценарии нескольких фич: удаление, правка и переезд проекта реестра                                    |

Почему правила доставки и ремонта, которые меняют состояние запуска, лежат в `runs/machine`, а не в
`delivery` и `observers`: они части одного `transition`. Эти фичи держат всё остальное — git, патчи,
планирование ремонта по очереди — и стоят выше `runs`.

Почему `repos` стоит в самом низу: почти каждая область сначала приводит путь к корню репозитория,
поэтому реестр не должен ни от кого зависеть. Счётчики запусков в ответе `repositories` собирает
представление, а проверки перед удалением — `compose`.

Почему `integrations` видит только `repos`: подключение привязано к проекту реестра, а действия над
очередью и запусками идут против стрелки через порт `IntegrationOperationsPort`, который подставляет
`app` из сервисов `queue` и `runs`. Значения секретов хранит не база, а `platform/secrets` (Keychain,
Secret Service или зашифрованный файл с внешним ключом) за портом `SecretStorePort`; новых пакетов
для этого нет. Конкретные адаптеры (`clients/<вид>/`) приходят отдельными изменениями.

Почему снятие тега живёт в `queue`, а не в `tags`: оно меняет запуски и элементы очереди, а `queue`
единственная фича, которая видит и `tags`, и `runs`.

Почему `swarm-edit` видит `runs`: редактор показывает схему конвейера и встроенные стадии с их
заданиями, а строят их `pipelineTopology` и тексты инструкций из `runs/types`. `runs` от правки
конфигурации не зависит, поэтому цикла нет.

- Фича не видит чужие репозитории, порты и адаптеры: только `types` и `services` фичи-владельца.
- Импорт из другой фичи идёт только через `<фича>/<вид>/index.ts`, внутри фичи — напрямую из файла.
  `index.ts` только реэкспортирует.
- Если вызов нужен «против стрелки», потребитель объявляет узкий интерфейс в `ports/`, а реализацию
  подставляет `app`.
- Сценарий нескольких фич, который по графу нельзя отдать одной, идёт в фичу `compose`: только
  `services/`, без хранения; её импортируют только представление и `app`. Сначала проверь, нет ли
  фичи, которая и так видит всех участников: тогда сценарий живёт в ней.

## 3. Правила пакетов и файлов

### 3.1. Один смысловой элемент — один файл

- одна группа подкоманд CLI — один файл `presentation/cli/commands/<group>.ts`;
- одна область IPC — один файл обработчиков `presentation/ipc/handlers/<area>.ts`, файл схем
  `ipc/contract/<area>.ts`, файл типов ответов `ipc/contract/responses/<area>.ts` и файл функций
  построения ответа `ipc/views/<area>.ts`;
- одна область HTTP — один файл `presentation/web/routes/<area>.ts`;
- одна группа инструментов MCP — один файл в `presentation/mcp/`;
- одна таблица или группа запросов — один файл `<фича>/repositories/<area>.ts`;
- одна область фичи — один файл `<фича>/services/<area>.ts`.

### 3.2. Пределы размера

Превышение делится по смыслу, предел не поднимается:

- файл `.ts`/`.tsx` — не больше 300 строк кода;
- функция, метод или компонент — не больше 80 строк кода;
- папка — не больше 12 файлов, не считая `index.ts`;
- класс — не больше 12 методов вне `private`.

Считаются строки кода: пустые строки и строки только с комментарием не входят, поэтому пределы не
наказывают за объяснения. Файлы данных пределам не подчиняются: словари `web/src/shared/i18n/locales`.

Старый код, не вошедший в пределы, записан в список исключений вместе с текущим размером. Список
только сокращается: запись нельзя добавить, размер в ней нельзя увеличить, а запись, которая больше
не нужна, проверка требует удалить. К концу перехода список пуст.

### 3.3. Транспортные формы отдельно от доменных

Схемы и типы ответов IPC (`ipc/contract`) и функции построения ответа (`ipc/views`) фичам не видны:
сервис принимает и возвращает доменные типы, обработчик переводит их в ответ. Текст для терминала
строит только `presentation/format`, а не сервис и не `ipc`. Этот подслой отдельный, потому что один
и тот же текст печатают и команды CLI, и инструменты MCP.

Тип ответа лежит в `ipc/contract`, потому что его читают клиенты демона: CLI, MCP, панель. Функция,
которая ответ строит, лежит в `ipc/views`, её вызывает только сам демон. Поэтому `ipc/contract` видит
только `types` фич: всё, что входит в форму ответа, объявлено в `types`, даже если считает это сервис.

Если одна и та же форма нужна фиче и транспорту, как запись расшифровки или строка каталога, тип
пишется руками в `<фича>/types`, а схема zod лежит в `ipc/contract`. Совпадение типа со схемой
проверяет компилятор: `expectTypeOf<z.infer<typeof schema>>().toEqualTypeOf<Type>()` в тесте
контракта. Выводить доменный тип из схемы нельзя: `types/` чистый и не видит ни `zod`, ни
представление.

### 3.4. Импорты и синтаксис

- Относительные импорты с расширением `.ts`; только стираемый синтаксис TypeScript: без `enum` и
  свойств-параметров, чтобы Node запускал исходники напрямую.
- `import type` для типов: проверка чистоты смотрит только импорты, которые выполняются.
- Классы — там, где есть зависимости и состояние (сервисы, репозитории); правила — чистые функции.
  Контейнера зависимостей нет: всё передаётся конструкторами в `app`.

## 4. Сборка, платформа, представление

```
src/
├── app/
│   ├── application.ts   # createApplication(options): база, наборы сервисов фич в порядке графа, порты
│   ├── wiring.ts        # подстановка портов «против стрелки»; проверка, что заданы все
│   ├── lifecycle.ts     # загрузка состояния и восстановление при запуске, порядок остановки
│   ├── daemon.ts        # startDaemon: блокировка, сокет, запуск и остановка
│   ├── agents.ts        # адаптеры claude и opencode для сервисов agents
│   ├── timings.ts       # длительности, которых ждёт демон; тесты их сокращают
│   └── maintenance.ts   # без демона: aip clean, адаптеры агентов для проверки конфигурации
├── platform/
│   ├── errors/          # AppError, виды ошибок; чистый модуль
│   ├── git/             # обёртка над git CLI: runner, рабочие деревья, скрытые ссылки, временный индекс
│   ├── sqlite/          # открытие базы, транзакции, миграции
│   ├── process/         # снимок ps, поиск исполняемых файлов
│   ├── paths/           # каталоги состояния, база, блокировка, сокет
│   └── build/           # корень пакета и дерева кода, версия, отпечаток сборки (§6.9)
└── presentation/
    ├── ipc/
    │   ├── contract/    # схемы zod по областям; responses/ — типы ответов для клиентов демона
    │   ├── views/       # доменное состояние → форма ответа; только функции
    │   ├── handlers/    # таблица «метод → обработчик»; один изменяющий вызов (§6.5)
    │   ├── services.ts  # набор сервисов фич, который читает и вызывает транспорт
    │   ├── snapshots.ts # чтение сервисов нескольких фич и вызов views: форма ответа
    │   ├── publisher.ts # подписчики, номера событий, реализация портов публикации
    │   ├── server.ts    # сокет, разбор конверта, рендер ошибок, подписки
    │   └── client/      # запрос, подписка, автозапуск демона
    ├── format/          # текст и цвет ответов для CLI и MCP
    ├── mcp/             # host и worker: тонкие обёртки над IPC; index.ts — вход для aip mcp
    ├── cli/
    │   ├── commands/    # по файлу на группу подкоманд
    │   └── program.ts   # commander, коды выхода, рендер ошибок
    └── web/
        ├── index.ts     # вход для cli: только реэкспорт
        ├── server.ts    # node:http, таблица маршрутов, рендер ошибок, защита хоста
        ├── errors.ts    # PanelError и таблица вид → статус
        ├── routes/      # по файлу на область
        └── panel/       # панель внутри демона, режим ожидания, состояние, браузер
```

Представление не собирает сервисы и не решает, что можно: это делают `app` и фичи. Тесты собирают
то же приложение и подменяют адаптеры опциями `createApplication`.

Панель сервисов не видит. Настройки `web` она получает параметром `readSettings: () => WebSettings`:
панель перечитывает их при каждом запуске, поэтому передаётся функция, а не значение.

`cli` запускает транспорты в своём процессе, поэтому видит их, но только через `index.ts`: `aip mcp`
берёт `presentation/mcp/index.ts`, а `aip web`, `aip daemon` и `aip daemon stop --web` —
`presentation/web/index.ts`. Обратных импортов нет: `mcp` и `web` не видят `cli`, поэтому цикла нет.

Панель поднимается тремя способами, и все три запускает `cli`:

- `aip web` поднимает отдельный сервер `startWebServer`: настройки команда читает сама один раз;
- `aip daemon` создаёт панель внутри демона и передаёт её в `startDaemon` как `PanelControl`;
- `aip daemon stop --web` запускает режим ожидания.

Функцию `readSettings` для двух последних строит `cli` из сервисов `swarm-config`. `app` панель не
импортирует.

## 5. Фича `src/feature/<фича>` (шаблон)

Виды папками, в корне фичи нет `.ts`. Виды заводятся по необходимости:

```
src/feature/<фича>/
├── types/          # домен: сущности, их правила, константы, коды ошибок; чистый вид
├── machine/        # только runs: transition, обработчики событий, диспетчеризация; чистый вид
├── ports/          # интерфейсы к другим фичам и внешним системам
├── services/       # сервисы областей: <area>.ts — области, create.ts — сборка фичи
├── usecases/       # крупные сценарии: <verb-noun>.ts, один метод run; их вызывает только services
├── repositories/   # доступ к данным: <area>.ts и rows.ts
└── clients/<имя>/  # адаптер внешней системы; реализует порт фичи, его подставляет app
```

- **Имена по виду:** репозиторий — `<Сущность>Repository`, сервис области — `<Область>Service`,
  набор фичи — `<Фича>Services`, порт — `…Port`, адаптер — `…Client`, сценарий — `…UseCase`.
- **Чистые виды** (`types/`, `machine/`) не импортируют `node:*`, внешние пакеты и любые файлы,
  которые их тянут. Часы, случайность и окружение приходят параметрами.
- **Сервис — по области, а не на фичу.** Область держит только нужные поля.
- **Сборка фичи — `services/create.ts`.** Функция `create<Фича>Services(deps)` получает базу, сервисы
  нижних фич и порты, создаёт свои репозитории и сервисы и возвращает набор областей. Поэтому
  репозитории не выходят из фичи, а `app` не знает её устройства. `index.ts` любого вида только
  реэкспортирует, кода в нём нет.
- **Репозиторий — только доступ к данным.** Можно: запросы, отображение строк в сущности, атомарная
  запись одной своей сущности (§7). Нельзя: часы, id, решения по результату запроса, вызов машины.
  Сценарий и транзакция на несколько сущностей — в сервисе области.
- **Репозиторий не выходит из фичи.** Другие фичи вызывают методы её сервисов.
- **Коды ошибок — у фичи** в `types/errors.ts`, общий тип — в `platform/errors` (§6.6).

## 6. Ключевые паттерны

### 6.1. Сборка

`createApplication` открывает базу, вызывает `create<Фича>Services` в порядке графа, создаёт адаптеры
и подставляет порты. Других мест, где «всё со всем соединяется», нет: `new` сервиса, репозитория,
сценария или адаптера вне `app` и файла `<фича>/services/create.ts` — ошибка раскладки, её ловит
проверка. Адаптеры создаёт только `app`: `clients/` больше никто не импортирует. Репозитории `app` не
импортирует: они создаются внутри `create.ts` своей фичи.

### 6.2. Порты и адаптеры

Внешние системы и обратные зависимости — интерфейс у потребителя, реализация отдельно. Альтернативные
реализации — разные типы одного интерфейса: `agents/ports` реализуют `agents/clients/claude` и
`agents/clients/opencode`. Адаптер импортирует свою фичу, сама фича его не импортирует. Типы внешних
библиотек не выходят из адаптера.

Платформа — не внешняя система для фичи: `services`, `repositories`, `usecases` и `clients`
импортируют `platform/git`, `platform/process` и другие модули напрямую, порта на них нет. Тесты ходят
в настоящий git, а там, где нужна подмена, значение передаётся параметром, как снимок процессов.

Если вызов идёт по стрелке графа, порт не нужен: `runs` вызывает `agents/services` напрямую. Тип,
который сервис отдаёт наружу, лежит в `types/` своей фичи, потому что чужие `ports/` не видны:
интерфейс `Runtime` объявлен в `agents/types`, а порт `agents/ports` описывает только создание
адаптера.

### 6.3. Машина состояний и эффекты

Изменение запуска — всегда `transition(state, event)`. Сервис применяет результат: сохраняет
состояние и исполняет эффекты. Эффект сам ничего не меняет в состоянии напрямую: его итог приходит
в машину новым событием. Новое поведение запуска начинается с события и его обработчика в
`runs/machine`, а не с условия в сервисе.

### 6.4. Последовательное исполнение

Все изменения состояния демона идут одной очередью (`serial`): обработчик запроса и событие от
агента не перемешиваются. Долгая работа — git, запуск агента — идёт вне очереди, а итог возвращается
в неё событием. Очередью владеет движок `runs/services/engine.ts`, другие фичи ходят через него.

### 6.5. Запрос к демону

Метод IPC → схема `ipc/contract` → обработчик из таблицы `ipc/handlers` → один изменяющий вызов
одного сервиса одной фичи → форма ответа через `ipc/snapshots.ts` и `ipc/views`. Таблица покрывает
все методы, полноту проверяет компилятор.

Изменение в обработчике одно: если действие меняет состояние двух фич, его место — в фиче, которая
видит обе, или в `compose`. Чтение для ответа может обращаться к нескольким фичам: `RunView` собирает
диффы, теги, артефакты и очередь, и это форма ответа, а не сценарий. Приведение пути к корню
репозитория делает сервис, а не обработчик. Когда метод должен идти в очереди `serial`, обработчик
оборачивает вызов сам, как и раньше.

Обновления клиентам уходят через порты публикации. Каждая фича объявляет свой узкий порт, а
`ipc/publisher.ts` реализует их все и один владеет подписчиками и номерами событий.

### 6.6. Ошибки: только вверх

1. Ожидаемая ошибка — `AppError` с видом и кодом: код объявлен в `types/errors.ts` фичи или в
   `platform`. Ошибки чужих систем адаптер переводит в `AppError` на своей границе.
2. Сервисы не ловят ошибки ради перевода в текст, транспорт сам решает, как их показать.
3. У каждого транспорта один рендер: `ipc/server.ts`, `mcp/tools.ts`, `cli/program.ts`,
   `web/server.ts`. Код выхода CLI от вида ошибки не зависит.

Через сокет IPC ошибка идёт только текстом: `{ ok: false, error }`. Код и вид через него не
передаются. Текст сообщения — контракт для пользователя.

Статус HTTP панель выбирает в одном месте, `web/server.ts`, в таком порядке:

1. `IpcError`, ошибка демона: кода у неё нет, поэтому статус выводит из текста функция
   `daemonErrorStatus`: 404, 409, 504, 502, иначе 400. Это осознанное исключение (§11). Новых
   ветвлений по тексту не добавляют.
2. `PanelError`, наследник `AppError` из `web/errors.ts`, ошибка самой панели: статус по таблице
   вид → статус, поле `code` в ответе только у ошибок, где оно задано явно.
3. Всё остальное — 502, в том числе `DaemonUnavailable` и `AppError` других областей.

`throw new Error` остаётся только для ошибок программиста. Паника в обработчике — тоже ошибка
программиста: всё ожидаемое возвращается как `AppError`.

### 6.7. Окружение

`process.env` читают только `src/cli/main.ts`, `src/app` и `src/platform`. Остальные получают
`environment` параметром; значения по умолчанию вида `environment = process.env` запрещены.

### 6.8. Доставка и git

Коммиты шагов и слияния групп живут в скрытых ссылках `refs/aip/<run>/…`. Доставка переносит дифф
группы в рабочее дерево через временный индекс. `git apply --3way --check` не годится для поиска
конфликтов: на конфликтующем патче он возвращает 0.

### 6.9. Расположение файлов

Пути от текущего файла (`import.meta.url`, `import.meta.dirname`, `require('../../package.json')`)
есть только в `platform/build`. Он отдаёт корень пакета, корень дерева кода (`src/` или `dist/`) и
версию; шаблоны, панель и отпечаток сборки строятся от этих значений. Иначе перенос файла меняет
значение пути незаметно: отпечаток начнёт покрывать только часть дерева, и демон перестанет
замечать пересборку.

## 7. Хранение

Одна база SQLite на машину, `node:sqlite`. Открытие, транзакции и список миграций — в
`platform/sqlite`; миграции идут одним списком, потому что порядок версий общий. Запросы — в
репозиториях фич, таблица принадлежит одной фиче:

| Таблица                              | Фича        |
| ------------------------------------ | ----------- |
| `runs`, `groups`, `attempts`         | `runs`      |
| `queues`, `queue_items`              | `queue`     |
| `repositories`                       | `repos`     |
| `tags`                               | `tags`      |
| `run_patches`                        | `delivery`  |
| `artifacts`                          | `artifacts` |
| `observers`                          | `observers` |
| `stats_attempts`, `stats_runs`, `stats_meta` | `stats` |
| `users`, `sessions`, `access_tokens`, `login_links`, `cli_login_codes` | `identity` |

Запрос читает и пишет только таблицы своей фичи. Если значение зависит от таблиц двух фич, как
следующий номер задачи, каждая фича отдаёт свою часть, а итог считает сервис.

Транзакции бывают двух уровней:

- **Запись одной сущности** атомарна внутри репозитория: запуск с группами и попытками, очередь с
  элементами, артефакт с проверкой прежней записи. Вызывающему не нужно о ней помнить.
- **Сценарий** на несколько сущностей или фич открывает сервис через `Database.transaction`. Внутри
  него вызываются только методы без своей транзакции: они называются `write…`, `delete…`, `drop…`.

`transaction` не вложенная (`BEGIN IMMEDIATE`), поэтому вызов `save…` внутри сценария падает сразу, а
не теряет атомарность незаметно. Снятие тега — такой сценарий: `queue` открывает транзакцию, а `tags`,
`runs` и `queue` меняют каждая свою таблицу, поэтому чужой репозиторий никто не импортирует.
Сценарий открывает `queue/services/task-tags.ts`, а восстановление после перезапуска —
`runs/services/recovery.ts`.

Файлы патчей и артефактов лежат в каталоге состояния за своими хранилищами в `repositories/`.

## 9. Веб-панель `web/`

```
web/src/
├── main.tsx
├── app/              # оболочка: App, маршруты, разделы, горячие клавиши, статус-бар
├── features/<область>/  # runs, queue, pipelines, specialists, topology, settings, tags, repositories
│   ├── index.ts      # единственный вход для других областей
│   └── …             # компоненты, состояние и правила области
├── shared/
│   ├── api/          # клиент HTTP, типы ответов, поток событий
│   ├── ui/           # дизайн-система без знания об областях
│   ├── lib/          # чистые помощники
│   └── i18n/         # словари en, es, ru, zh
└── index.css
```

- `shared` не импортирует `features` и `app`; `features` не импортирует `app`.
- Другая область — только через её `index.ts`. Граф областей ацикличен.
- Запросы к серверу идут только через `shared/api`.
- Из `src/` панель берёт только типы (`import type`), и только из `presentation/ipc/contract/index.ts`
  и `feature/<фича>/types/index.ts`: так контракт ответов один, а код сервера в сборку панели не
  попадает. Тесты панели могут импортировать и значения из `types`, например цвета тегов.
- Любой текст панели — ключ во всех четырёх словарях.
- Логика, которую можно проверить без браузера, лежит рядом в обычном `.ts`, а не внутри компонента.
- Пределы §3.2 действуют и здесь: большая форма делится на секции.

## 11. Осознанные отступления от образца

Каждый пункт — решение, а не недоделка.

- **Комментарии в коде остаются.** Они объясняют, почему код написан именно так; пределы размера
  считают только строки кода.
- **Машина состояний вместо сервисов с транзакциями.** Изменения запуска идут через чистый
  `transition`, поэтому появился вид `machine/` и чистый вид вообще.
- **Нет `pkg/`.** Самостоятельных библиотек нет, всё лежит в `src/platform`.
- **Точка входа остаётся `src/cli/main.ts`.** На `dist/cli/main.js` указывают `bin`, упаковка и
  настройки плагина.
- **SQLite вместо Postgres:** нет аренды строк и транзакции в контексте, один процесс владеет базой.
- **Код ошибки не передаётся по IPC:** форма ответа `{ ok: false, error }` — действующий контракт.
  Поэтому статус HTTP для ошибок демона панель по-прежнему выводит из текста сообщения (§6.6), пока
  код не идёт по сокету.

4. Тесты — чистый в `test/feature/runs`, сквозной в `test/daemon`.

### Добавить таблицу или колонку

Миграция — следующая запись в `platform/sqlite/migrations.ts`, запросы — репозиторий фичи-владельца.
Строка в таблице §7, если таблица новая.

1. Виды по §5, строка в графе §2 и в таблице графа `test/layout/rules.ts`.

3. Если нужен вход в представление — обработчики и контракт по рецепту выше.

### Добавить внешнюю систему

Порт — `<фича>/ports/`, адаптер — `<фича>/clients/<имя>/`, подстановка — `app`. Тесты подменяют

## 13. Состояние перехода

Шаги идут по порядку; следующий шаг начинается после зелёного `npm run check` предыдущего. Перенос
файлов начинается только когда незакрытая работа в репозитории завершена, и на время шага другие
задачи в этом репозитории не запускаются.

| Шаг | Что меняется                                                                    | Сейчас        |
| --- | ------------------------------------------------------------------------------- | ------------- |
| 1   | этот документ, проверки раскладки, список исключений                            | сделан        |
| 2   | `src/app`, разрыв цикла демона, `platform/git`, `platform/process`, окружение    | сделан        |
| 3   | `src/config` → `swarm-config`, `swarm-edit`, `platform/paths`                   | сделан        |
| 4   | единая модель ошибок `platform/errors`                                          | сделан        |
| 5   | `src/core` → `types` и `machine` фич                                            | сделан        |
| 6   | `src/store` → `platform/sqlite` и репозитории фич                               | сделан        |
| 7   | `Daemon` и `Executor` → сервисы фич, `src/runtime` → `agents`, обработчики IPC  | сделан        |
| 8   | `src/protocol`, `src/mcp`, остаток `src/cli` → `src/presentation`               | сделан        |
| 9   | `web/src` → `app`, `features`, `shared`                                         | сделан        |

Пока шаг не сделан, в коде действует старая раскладка:
